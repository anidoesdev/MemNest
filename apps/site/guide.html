How it works

Memnest has two paths. The write path turns raw content into facts in the background. The read path finds the current facts for a question and fits them into a token budget. The live preview runs both in your browser.

Write path · add() returns after step 2; the rest runs in a job
  1. add()chat turns, markdown or text
  2. redact + chunksecrets stripped, chunks indexed
  3. extractone model call per quiet session
  4. screendrop pronouns, secrets, low confidence
  5. resolvenew · duplicate · updates · extends
  6. writeone transaction, with provenance
Read path · search()
  1. query+ scope + token budget
  2. lexical ∥ vectorrun in parallel
  3. RRF fusek = 60
  4. filterlatest, not forgotten, not expired
  5. rerankoptional, LLM
  6. packmemories, then chunks, to budget

The key step is resolve. For each new candidate fact, Memnest retrieves up to 10 similar current memories and decides how they relate: new (nothing similar; no model call), duplicate (reinforce the existing memory), updates (new version served, old one kept as not-latest) or extends (linked, both current). Identical text is caught without a model call.

When the model gives an invalid answer, Memnest retries once, then writes the fact as new. A missed relation can be fixed later; a wrong updates would hide a true fact.

Key concepts

container tag
Whose memory this is, e.g. user:123 or customer:acme. A hard boundary: nothing crosses between containers. Every call takes a scope built with scopeOf(tag).
document
Raw input: a conversation ({ role, content } turns), markdown or text. Split into chunks that are searchable right away.
customId
A stable id for a document. Re-sending with the same id creates a new version; in batched mode, documents that share it form one session.
memory
One atomic, self-contained fact with a kind (fact, preference or episode), a confidence, an optional expiry, and links to its sources.
latest / not-latest
When a memory is updated, the new version is latest and the old one is kept but no longer served.
forgotten
A soft delete by a person. Out of search and profiles, still visible for audit.
provenance
Every memory points to the document and extraction run that produced it. Stores refuse memories without one.
extraction run
The log of one extraction job: candidates, decisions with reasons, and redacted rejections. memnest runs shows them.
trace
Returned by every search: each candidate's lexical and vector rank, fused score, tokens, and whether it was included or why not.
profile
A cached, prompt-ready summary of a container: stable facts plus recent activity, each line citing its memories.

Quickstart: see a fact change in two minutes

No model or database needed. This uses SQLite and direct writes.

  1. Install the CLI
    npm install -g @memnest/cli
  2. Create a database and write a fact
    memnest migrate --db demo.db
memnest memories add "The user prefers Postgres over MongoDB for the payments database." \
  --container user:123 --db demo.db          # prints the new memory's id
  3. Write a fact that replaces it
    memnest memories add "The user moved the payments database to MySQL." \
  --supersedes <id-from-step-2> --container user:123 --db demo.db
  4. Ask
    memnest search "what database does this user use?" --container user:123 --budget 200 --db demo.db

    You get the MySQL memory. The trace lists the Postgres memory as excluded, not-latest.

  5. Look at the history
    memnest memories list --all --container user:123 --db demo.db
memnest lineage <mysql-id> --container user:123 --db demo.db

Direct writes skip extraction, so you set relations yourself with --supersedes or --extends. With a model configured, memnest ingest finds them for you (see Ingest & extraction).

MCP clients

memnest mcp gives any MCP client long-term memory over one container. It speaks MCP over stdio, which is how local clients launch servers.

ToolWhat it does
recallCurrent facts relevant to a question, within a token budget. Says how many older facts were left out and why.
rememberStores facts, one sentence each. Skips exact duplicates. supersedes records a change; extends adds detail.
ingestHands raw notes or transcripts to extraction. Searchable at once; memories appear once extraction runs.
forgetStops serving a wrong memory; it stays in history.
historyWhere a memory came from and how it changed.
profileA prompt-ready summary. Also the resource memnest://profile.
  • Local by default. Memories live in ~/.memnest/memnest.db, created and migrated on first use. --db, MEMNEST_DB or MEMNEST_DATABASE_URL change that.
  • Shared through a server. --url https://memnest.example.com with MEMNEST_KEY set. A key made with memnest keys create --container user:me fixes the container.
  • The model never picks the container. It's configuration, so a prompt injection can't reach someone else's memory. --read-only leaves only recall, history and profile.

Use it from code

Embedded, no server

import { createMemnest, scopeOf } from '@memnest/core';
import { createSqliteStore } from '@memnest/store-sqlite';

const store = createSqliteStore({ filename: 'memnest.db', autoMigrate: true });
const memnest = createMemnest({ store, queue: store.jobQueue() });

await memnest.add({ containerTag: 'user:123', content: [{ role: 'user', content: 'I prefer Postgres.' }] });
const { memories, chunks, trace } = await memnest.search('database', scopeOf('user:123'), { tokenBudget: 200 });

Extraction needs a completion provider and a worker: pass completion to createMemnest and call memnest.startWorker(), or run memnest worker. Until then chunks are searchable but no memories are extracted.

Postgres with embeddings

import { ollamaEmbeddings } from '@memnest/providers';
import { createPostgresStore } from '@memnest/store-postgres';

const store = await createPostgresStore({ connectionString: process.env.MEMNEST_DATABASE_URL });
const memnest = createMemnest({ store, queue: store.jobQueue(), embedder: ollamaEmbeddings({ model: 'nomic-embed-text' }) });

Against a server

import { createMemnestClient } from '@memnest/client';

const memnest = createMemnestClient({ baseUrl: 'http://localhost:8787', apiKey: process.env.MEMNEST_KEY });

The main calls: add, search, searchMemories, searchDocuments, profile, addMemories, listMemories, getLineage, forget, graph, deleteDocument, deleteContainer and listExtractionRuns. Errors are MemnestErrors with a code such as validation, not_found or scope_violation.

Server & dashboard

  1. Start Postgres + pgvector and the server
    docker compose up -d   # server on http://localhost:8787
  2. Create an API key (shown once; only its hash is stored)
    docker compose exec server memnest keys create --name admin
docker compose exec server memnest keys create --name acme-bot --container customer:acme   # scoped
  3. Write and search over REST
    curl -X POST localhost:8787/v1/memories -H "Authorization: Bearer $KEY" -H 'content-type: application/json' \
  -d '{"containerTag":"user:123","memories":[{"content":"The user prefers Postgres over MongoDB."}]}'
curl -X POST localhost:8787/v1/search -H "Authorization: Bearer $KEY" -H 'content-type: application/json' \
  -d '{"containerTag":"user:123","query":"what database does this user use?","options":{"tokenBudget":200}}'
  4. Open the dashboard at http://localhost:8787 and sign in with the key.
Graph
Every memory. Colour is kind, size is reinforcement; superseded memories are faded, forgotten ones hollow. Above 2,000 memories it groups topics into clusters.
Lineage
One memory, what it replaced, what extends it, and its source documents.
Retrieval trace
Every candidate for a query, with the budget line drawn across the list.
Timeline
A topic's facts over time, each change dated.
Detail
Content, kind, confidence, validity, versions and sources, plus Forget. Memories are never edited: a wrong one is forgotten.

Connect a model

Extraction, resolution and model-written profiles need a completion model; semantic search needs an embedding model. They can come from different providers: Ollama, or any OpenAI-compatible endpoint.

# Ollama for everything (embeddings default: nomic-embed-text)
export MEMNEST_PROVIDER=ollama MEMNEST_COMPLETION_MODEL=llama3.1:8b

# OpenAI (embeddings default: text-embedding-3-small)
export OPENAI_API_KEY=sk-... MEMNEST_COMPLETION_MODEL=gpt-4.1-mini

memnest providers check   # calls both endpoints
memnest providers env     # every supported variable

Prefer Ollama's native adapter to its /v1 route: it enforces the JSON schema. For servers that only support JSON mode, set MEMNEST_STRUCTURED_OUTPUT=json_object.

Ingest & extraction

memnest ingest session.json --container user:123 --custom-id session-1   # .json turns, .md or .txt
memnest worker                     # or: memnest jobs run
memnest runs --container user:123  # decisions and rejections, with reasons
  • batched (default): documents sharing a customId form a session, extracted once it has been quiet for 30 seconds (at most 10 minutes after its first unextracted version). If the session grows, only the new part is extracted.
  • instant: extract each document right away. For tests and demos.
  • none: index chunks only.

Candidates are rejected for unresolved pronouns, anything the redactor catches, confidence below 0.5, an expiry already past, malformed output, or duplicates within the batch. A failed job never loses the document: its chunks stay searchable and memnest jobs retry <jobId> requeues it.

Search & the trace

search() returns memories (facts for the prompt), chunks (source text for grounding) and a trace. Memories are packed first; chunks share what's left.

OptionDefaultWhat it does
tokenBudget2000Most tokens to return. budget.used is exactly the included total.
candidates50Pool size from each retriever.
rerankoffLLM rerank of the top 20; drops scores below 0.2.
minVectorScore0Ignore vector hits at or below this similarity.

A candidate is excluded as not-latest (replaced), forgotten, expired, rerank or budget. When vector search can't run, trace.degraded says why: SQLite has no vector search, no embedding provider is configured, the container has no embeddings yet, or the query embedding failed.

Profiles

const { text, stable, recent, stale } = await memnest.profile(scopeOf('user:123'));
  • A cached read, rebuilt after 10 memory changes or when 24 hours old, never on every write.
  • Safe even when stale: forgetting or replacing a memory removes every profile line that cites it immediately.
  • Model-written profiles are checked: every line must cite real memories, with no pronouns or secrets, or the deterministic builder answers instead.

Security

  • Containers are hard boundaries, in the engine and over HTTP. Scope comes from the key, in middleware; handlers never read a container from the request.
  • Keys look like mnk_<id>_<secret>; only argon2id hashes are stored. memnest keys revoke ends a key's sessions too.
  • Secrets never reach storage. Redaction runs before hashing, chunking or saving.
  • Not included yet: rate limiting and per-key permissions beyond container scope.

Troubleshooting

I ingested a conversation but no memories appeared

Extraction needs a completion model and a worker. Check memnest providers check, then run memnest worker. In batched mode it also waits 30 quiet seconds. memnest runs shows what was rejected and why.

The trace says lexical-only

Read the reason in degraded. SQLite has no vector search: use Postgres. No embedding provider: set MEMNEST_EMBEDDING_PROVIDER. No embeddings yet: run memnest backfill --container <tag>.

An error names two embedding providers

That's the dimension lock: a container keeps the first embedding provider it saw so vectors never mix. Go back to it, or use a new container.

The MCP server doesn't show up in my client

Run the command from the config in a terminal: it should print Memnest MCP server on stdio to stderr and wait. Missing --container is the usual cause. Clients show a server's stderr in their MCP logs.

The store refuses to open: pending migrations

Run memnest migrate, or pass autoMigrate: true to createSqliteStore. (memnest mcp migrates its SQLite database itself.)
