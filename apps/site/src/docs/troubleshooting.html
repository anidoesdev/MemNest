Memories

I ingested a conversation but no memories appeared

Extraction needs a completion model and a worker. Check memnest providers check, then run memnest worker (or memnest serve with MEMNEST_WORKER=auto).

In batched mode it also waits for the session to be quiet for 30 seconds. To see it immediately, ingest with --extraction instant and run memnest jobs run.

If the job ran but wrote nothing, memnest runs --container <tag> lists each rejected candidate with its reason: usually low-confidence (small talk) or unresolved-pronoun.

The same fact was stored twice

Resolution needs a completion model; without one, only exact text matches are caught. Check memnest runs: decisions marked no-neighbors mean nothing similar was retrieved, which also happens when the two wordings share no keywords and the container has no embeddings. Run memnest backfill --container <tag>, or use Postgres for vector search.

An old fact is still being served

Look at the trace: if the old memory is included rather than not-latest, no updates relation was recorded, so Memnest does not know they are the same fact. Link them with a direct write (--supersedes), or forget the old one.

Search

The trace says lexical-only

Read the rest of degraded. SQLite has no vector search, so use Postgres + pgvector for semantic recall. no embedding provider configured: set MEMNEST_EMBEDDING_PROVIDER. container has no embeddings yet: run memnest backfill --container <tag>, which embeds what was written before the provider existed.

An error names two embedding providers or dimensions

The dimension lock. A container records the first embedding provider and dimension it saw and refuses others, so incompatible vectors are never compared. Go back to the original model, or use a new container.

Recall returns less than the budget allows

Vector hits at or below minVectorScore (default 0) are dropped, because vector search returns something for every query. Candidates also have to survive the latest/forgotten/expired filter. The trace lists everything that was considered.

Chat clients

The MCP server does not appear in my client

Run the exact command from your config in a terminal. It should print Memnest MCP server on stdio: … to stderr and then wait. A missing --container (or MEMNEST_CONTAINER) is the usual cause.

Clients show a server's stderr in their MCP logs; check there first. In Claude Desktop, quit from the system tray and reopen: closing the window does not reload the config.

It works in a terminal but not in Claude Desktop (Windows)

Desktop apps do not always inherit your PATH, so npx may not resolve. Use the full path to Node as command, with the CLI's path as the first argument, and double every backslash in JSON.

The assistant remembers nothing between chats

Check both clients point at the same --container and the same database. memnest memories list --container <tag> --db ~/.memnest/memnest.db shows what is really stored. Also confirm the client is actually calling recall: most show tool calls in the conversation.

Running it

The store refuses to open: pending migrations

Run memnest migrate, or pass autoMigrate: true to createSqliteStore. memnest mcp migrates its own SQLite database. Upgrading from 0.1.x needs a migration for the API key and session tables.

An extraction job failed

The document is not lost: its chunks stay searchable. Find it with memnest jobs --container <tag> --status failed and requeue it with memnest jobs retry <jobId>. Permanent errors (a bad configuration) fail immediately rather than retrying; the run records the message.

The dashboard will not sign in

The session cookie is SameSite=Strict and there is no CORS, so the dashboard must be served by the server itself: memnest serve --dashboard apps/dashboard/dist. In development, the Vite dev server proxies /v1 to it.
